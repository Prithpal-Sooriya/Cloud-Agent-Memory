# Playbook: MetaMask/metamask-core

This is an evolving playbook. Rules are structured as itemized bullets with unique IDs to allow for incremental updates and to prevent "context collapse".

## Strategies and Hard Rules (SHR)

These are environment-specific guidelines and mandatory workflows.

- **[shr-001] Environment Setup**: To initialize the development environment, run `nvm use && yarn install` in the root directory.
- **[shr-002] Project Type**: This is a monorepo that contains many packages.
- **[shr-003] Type Checking**: To type-check changes, run the **root** `yarn build` (`tsc --build tsconfig.build.json`), which resolves TS project references across the monorepo in dependency order. Package-level `yarn build:clean` fails with TS6305 ("Output file .../dist/index.d.ts has not been built") whenever workspace dependencies lack `dist/` output (fresh clone or after `build:only-clean`); use it only when dependency dists already exist, or run the root build first.
- **[shr-004] Changelog Requirements**: Once a PR is made, update the related files changelog to reflect the file changes. Add the correct PR link to the changelog. Changelog users are developers consuming the package.
- **[shr-005] Changelog Exceptions**: For ESLint cleanup PRs (adding return types, renaming identifiers, fixing lint violations) that don't change implementation behavior, **do not add changelog entries**. Changelogs are for changes that impact consumers of the package.
- **[shr-006] Review-Comment Resolution Requires Code Push**: When asked to resolve PR review comments, implement the requested code changes and push in the same turn; do not stop at drafting reply text. Include commit hash and push confirmation. If the request is wording-only, explicitly state that no code changes were made.
- **[shr-007] Regenerate messenger action types**: When adding methods to a controller/service's `MESSENGER_EXPOSED_METHODS` in metamask-core, regenerate the `*-method-action-types.ts` file with `yarn messenger-action-types:generate` (package script backed by `packages/messenger-cli`); never hand-edit it. Method JSDoc is copied verbatim into the generated public action-type docs — write the JSDoc carefully before generating.
- **[shr-008] Terse JSDoc/comments only**: In MetaMask repos, keep JSDoc to a one-to-two-line summary plus only the necessary `@param`/`@returns`/`@throws` tags. No multi-paragraph essays, rationale, or inline examples in code comments — rationale belongs in the PR description or README. Remember method JSDoc is copied verbatim into generated files (e.g. `*-method-action-types.ts`), so verbosity is amplified.

## Useful Code Snippets and Templates (CODE)

Reusable patterns and specific syntax requirements.

- **[code-001] Integration-test house style — follow the skill**: When writing any new `*.integration.test.ts` in MetaMask/core (assets-controller fast-lane/controller pipelines especially), load and follow `skills/integration-test-house-style/SKILL.md` in this repo (raw: https://raw.githubusercontent.com/Prithpal-Sooriya/Cloud-Agent-Memory/main/skills/integration-test-house-style/SKILL.md) — it carries the 8-step house-style template (header docblock after imports, response-surface tables, `describe.each` rows, one `run<Thing>` helper, tiny named helpers, `toStrictEqual` assertions, shared fixture builders, numeric-range comments) plus the oxlint/jest/jsdoc authoring-gotchas checklist. Exemplar: `packages/assets-controller/src/pipeline/buildFastFetchSources.bsc-spam-token-filtering.integration.test.ts`.
- **[code-002] Separate coverage reports per jest suite type**: To give integration and unit suites in metamask-core their own coverage reports, create one `jest.config.<kind>.cjs` per suite kind that `merge`s `../../jest.config.packages.cjs`, sets a distinct `coverageDirectory` (`coverage/unit`, `coverage/integration`), and selects files via `testMatch` (integration) or `testPathIgnorePatterns` (unit — must restate `/node_modules/` since user keys REPLACE Jest defaults), plus a `package.json` script `NODE_OPTIONS=--experimental-vm-modules jest --config jest.config.<kind>.cjs`. Do NOT use `projects` + `--selectProjects`: Jest 30 reads coverageDirectory/coverageThreshold/coverageReporters from the global config only, so a single invocation cannot write two coverage directories. Keep the default `jest.config.cjs` untouched so `yarn test`/CI keep the combined run. Precedent: wallet-cli `jest.config.e2e.cjs`; assets-controller unit/integration split in PR #10625.

## Troubleshooting and Pitfalls (TS)

Lessons learned from past execution failures or resource constraints.

- **[ts-001] Lint Cleanup Process (Oxlint, not ESLint — ESLint was migrated away)**: Format with **oxfmt** (`yarn lint:misc`), not Prettier — `yarn prettier --check` passes on files that `lint:misc:check` rejects (oxfmt also sorts imports; Prettier does not). There is no `eslint` script anymore; ESLint tooling was removed during the Oxlint migration. Use two commands in sequence:
  1. `yarn oxlint <files> [--fix]` (or repo-wide `yarn lint:oxlint [--fix --prune-suppressions]`) for lint violations.
  2. `yarn lint:misc --write <files>` (oxfmt), then verify with `yarn lint:misc:check` — the CI `Lint (lint:misc:check)` job.
- **[ts-002] Changelog CI Requirement (docs/comment-only PRs → `no-changelog` label)**: The CI "Check changelog" job fails if you modify a package without updating its `CHANGELOG.md` — **unless** the PR carries the `no-changelog` label. For behavior-free changes (comments, docs, README examples, ESLint cleanups — see [shr-005]) skip the changelog entry and instead: `gh pr edit <num> --repo MetaMask/core --add-label no-changelog`. For real changes, add entries under `## [Unreleased]` with a link to the PR: `([#XXXX](https://github.com/MetaMask/core/pull/XXXX))`.
- **[ts-003] Private Member Hash Syntax**: The repo enforces using hash syntax (`#memberName`) for private class members instead of TypeScript's `private memberName`. ESLint will flag `private readonly` as violations.
- **[ts-004] superstruct StructError message format**: In @metamask/superstruct v3.4+, a failing `define`/`definePattern` struct (e.g. `CaipAssetTypeStruct`) throws ``Expected a value of type `StructName`, but received: `value` `` — not classic superstruct's "Expected a StructName, but received ...". Nested failures are prefixed with the dotted path: `At path: importedAssets.1 -- Expected a value of type ...`. Write jest `toThrow` regexes accordingly (e.g. /At path: importedAssets\.1 -- Expected a value of type `CaipAssetType`/u).
- **[ts-005] Include eslint-suppressions.json in the oxfmt step**: `yarn eslint --fix --prune-suppressions` rewrites `eslint-suppressions.json` without a trailing newline, failing `yarn lint:misc:check`. After running it, include `eslint-suppressions.json` in the follow-up `yarn lint:misc --write eslint-suppressions.json` (or run `yarn lint:misc --write` from the repo root) before checking.
- **[ts-007] Open same-repo PRs against MetaMask/core — fork PRs structurally fail CI**: "Check changelog" and "Validate changelog diffs" resolve `origin/<head-ref>` inside MetaMask/core — github-tools `check-changelog@v1` checks out `repo: github.repository` + `ref: github.head_ref`; `check-merge-queue-changelogs` runs `git merge-base origin/<base> origin/<pr-branch>` — so ANY fork-sourced PR fails them (`fatal: Not a valid object name origin/<branch>`) regardless of content. The account has write access to MetaMask/core (verify: `gh api repos/MetaMask/core/collaborators/Prithpal-Sooriya/permission` → `write`; `origin` remote is SSH).
  1. Preferred flow: `git push origin <branch>` (feature branch to upstream via SSH) → `gh pr create --repo MetaMask/core --base main --head <branch>` — all checks green.
  2. If a fork PR already exists: prove changelog content locally with `node .github/actions/check-merge-queue-changelogs/check-changelog-diff.cjs <base-changelog> <pr-changelog> <merged-changelog>` (exit 0 = content fine), then close the fork PR with an explanatory comment, open the same-repo PR, update changelog links to the new PR number, and delete the redundant fork branch (`git push git@github.com:Prithpal-Sooriya/core.git --delete <branch>`).
- **[ts-008] MetaMask/core PR review conventions + transient-state concurrency pattern (from PR #10230 round 1)**: Reviewer conventions, concurrency pattern, and thread hygiene:
  1. Keep PRs minimal — no explanatory doc comments on new state fields/metadata/helpers (repo lint does not require JSDoc; strip to zero unless pre-existing style has them).
  2. Changelog entries are ONE sentence — no enumeration of new exports.
  3. After any public-method JSDoc change, re-run `yarn workspace <pkg> run messenger-action-types:generate`; verify the generated file has ZERO diff vs main if the reviewer asked for no generated-file churn.
  4. Prefer simple value unions (`'loading' | 'loaded'`) over rich encodings (trigger unions) unless the reviewer asks for context — the reviewer explicitly said "it is meant to be a 1-time loading for now".
  5. Transient UX state attached to mutex-serialized fetches: set the marker at EVENT time BEFORE `await mutex.acquire()` (queued switches then mark their accounts immediately) and settle to the terminal value in an OUTER `finally` wrapping the entire mutex section — never only inside the post-mutex fetch (Bugbot flags exactly this as "Queued switch omits loading status").
  6. Thread hygiene: reply via `gh api repos/MetaMask/core/pulls/<n>/comments --input -` with `{"body":..., "in_reply_to":<commentId>}`, then resolve each with GraphQL `resolveReviewThread(input:{threadId:"PRRT_..."})`; re-requesting review from the PR author's own account 422s — human re-approves manually.
- **[ts-009] Write repetitive tests as it.each tables**: In MetaMask repos, when new tests repeat the same body across methods/inputs/statuses (mirrored method pairs, error-status sweeps, malformed-input cases, cache-invalidation trios), write them as `const testCases = [...] as const` + `it.each(testCases)('...', ...)` from the start — split per scenario, not one massive array. House patterns: `it.each([401, 500])('throws ... %s')`, object rows with `$prop` title interpolation, `describe.each` for mirrored describes. Use `as const` rows so `service[method]` indexing stays type-safe (spread readonly `ids` with `[...ids]` at call sites), and remember arrow functions in table rows need explicit return types for `explicit-function-return-type`.
- **[ts-014] Kandev: `@metamaskbot <command>` comments re-trigger non-actionable auto-fix rounds**: `@metamaskbot <command>` comments are bot triggers, not review feedback → classify non-actionable; no file changes, no commit, no push, no local verification. Same for branch moves caused by the human merging main (213-file diffs that are pure main content — verify by diffing your last known head against the new tip; if everything is main's, do nothing).
  - Serve each repeat round with a single state-check call pair (CLI `pr view` failing/pending/mergeable/review + GraphQL unresolved-thread count) — do not re-audit call sites or re-run suites for identical snapshots.
  - The `report_pr_auto_fix_outcome_kandev` tool is frequently absent from the agent toolset; per protocol fallback, state the outcome classification (non_actionable/action_taken/blocked) explicitly in the reply text.
  - Distinguish from pending-only rounds (also non-actionable, per Kandev rules): publish-previews rounds show a COMPLETE green snapshot, so no polling is warranted at all.
- **[ts-017] Post-#9651 (main) pipeline wiring changes**: `getAssetsState` moved from the `executeAssetsPipeline` ctx param into the constructors of `TokenDataSource`, `PriceDataSource`, `DetectionMiddleware`, and `CustomAssetGraduationMiddleware` (all now require it); `AssetsControllerStateInternal` was renamed to `AssetsControllerState` (types.ts); import `Caip19AssetId` from `../types.js`, not `@metamask/utils` (utils dropped the export). Adapting old test wiring to these: add `getAssetsState: () => state` to every such construction and drop it from `executeAssetsPipeline` calls.
- Triage shortcuts: pipeline tests where an API records zero batches ⇒ look for a constructor option left undefined (middleware errors are swallowed, never thrown). oxlint "error typed value" on a test fixture ⇒ grep its type imports against current `types.js` — a renamed/removed type poisons everything downstream.
- **[ts-020] Extending an options-object parameter in TS tests is a 3-site edit: the destructure line, the type annotation, AND the harness helper's JSDoc `@param options.<name>` (oxlint jsdoc rules fail otherwise).** Run the single test file immediately after — babel-jest parses in <10s and catches all three misses at once. Also: when an edit's oldText ends at `}>`, check the following `{` before replacing.
- **[ts-022] The comment bar for NEW code is stricter than "precedent density"**. For new tests/fixtures in MetaMask repos:
  - JSDoc = ONE-line summary + only the tags oxlint requires (`@param options.x` members when the object is documented, `@returns`). No rationale paragraphs, no "Ordering carries N invariants" essays, no "Extracted from … mirroring …" history — that belongs in the PR description.
  - Inline `//` comments only when the test title/constant name does NOT already carry the fact. "The captured USDC price is pegged around one dollar" (explains a numeric range) is keepable; anything restating the `it(...)` title or the flag name is slop — delete.
  - Constant one-liners: subject only ("USDC, lower case as the websocket reports it."), no narrative ("first seen by the wallet on the websocket …").
  - Before pushing new test code, grep the diff for `//` and JSDoc line-count: every block >4 lines must be tags, not prose.
- **[ts-023] pi guard blocks ALL local `git commit` when global `commit.gpgsign=true` (even `--no-gpg-sign`)**: to ship a PR from the pi harness, create the commit server-side via `gh api` — `GET git/ref/heads/main` + `GET git/commits/{sha}` (base tree) → `POST git/trees` (base_tree + inline `{path, mode:'100644', type:'blob', content}` entries) → `POST git/commits` (message/parents + `author` object satisfying [shr-001]) → `POST git/refs` (branch) — then `gh pr create` + `--add-label no-changelog`, and sync local with `git fetch origin <branch> && git checkout -B <branch> origin/<branch>`. Check `git diff --name-only <local-base> <new-main> -- <pkg>` for drift first; the API commit is unsigned (GitHub signs the squash-merge).
- **[ts-024] State-shape features vs main's snapshot integration tests**: When merging a PR that adds/renames controller state fields into a main that gained snapshot-based integration tests ("generates snapshot (source of truth)", `__snapshots__/*.snap`), expect exactly those snapshot files to fail after the merge. Verify the jest diff shows ONLY the feature's new fields, then run `yarn jest --no-coverage --ci -u` scoped to the affected test FILE (never blanket-update the package). The pipeline-level snapshots (source-building only, no controller state) do NOT change.
- **[ts-025] Verify an existing PR's head repo before pushing**: Before pushing to update an existing PR, check `gh pr view <n> --repo <upstream> --json headRepositoryOwner,headRefName`. Fork-sourced PRs (head on `Prithpal-Sooriya/core`, remote `personal`) are only updated by pushes to `personal` — a push to `origin` (upstream `MetaMask/core`) does NOT update the PR and leaves a stray branch on upstream; delete it with `git push origin --delete <branch>`. Do not confuse with [ts-007]'s flow for NEW PRs (push feature branches to `origin` and open same-repo PRs).
- **[ts-026] Fork-PR pushes containing workflow files must go via SSH**: The `personal` fork remote (OAuth token) rejects pushes whose commits touch `.github/workflows/*` ("refusing to allow an OAuth App to create or update workflow … without `workflow` scope") — and any merge of a moved main carries workflow changes. For fork-sourced PRs (per the [ts-025] entry from issue #219), push with `git push git@github.com:Prithpal-Sooriya/core.git <branch>` (SSH, same key as `origin`) instead of the `personal` URL. For [shr-001] on merge commits, `git merge` has no `--author` flag — use `GIT_AUTHOR_NAME`/`GIT_AUTHOR_EMAIL` env vars.
- **[ts-027] When GitHub REST API calls 403 with "rate limit exceeded" (even though `gh api rate_limit` shows quota remaining — secondary rate limiting), pivot endpoints instead of retrying**:
  1. use GraphQL — `gh pr view <num> --json statusCheckRollup` or `gh api graphql -f query=...` — which runs on a separate quota and returns per-check `detailsUrl`;
  2. fetch CI job logs via `gh api repos/{owner}/{repo}/actions/jobs/<job-id>/logs` where `<job-id>` is parsed from the `statusCheckRollup` detailsUrl (`.../actions/runs/<run>/job/<job-id>`);
  3. avoid `gh run list` and `commits/<sha>/check-runs` REST endpoints on repeat.
- **[ts-028] MetaMask/core PR CI checks out `refs/pull/N/merge`, not the PR head**: Test/lint jobs run on the merge of your branch into the LATEST main — main moving mid-session silently changes what CI executes. When a CI failure references code/tests absent from your branch's tree, do not distrust the log: `git fetch origin refs/pull/<N>/merge`, inspect `FETCH_HEAD`'s tree (blob-shas vs your HEAD), then merge the new main locally and reconcile (expect the state-snapshot treatment per the snapshot rule). Keep merging main until `refs/pull/N/merge` ≡ your branch.
- **[ts-029] Auto-committed merges bypass the author flag + tool quirks on this macOS env**: `git merge --no-edit` auto-commits clean merges without `--author`; after every clean merge run `git log -1 --format="%an <%ae>"` and `git commit --amend --no-edit --author="Prithpal Sooriya <prithpal.sooriya@gmail.com>"` before pushing. For exact literal multi-site replacements use Python `str.replace` with a count assertion (BSD sed "bad flag" errors and perl `-pi` can silently no-op). Direct jest invocations need `--watchman=false` (homebrew watchman dyld-crashes on libfmt.11 after the fmt 12 upgrade, exiting 0 with zero test output).
- **[ts-030] New jest config files need 3 lint steps in metamask-core**: For every new `packages/*/jest.config.*.cjs`:
  1. add its glob to the jest-config group in root `oxlint.config.ts` (gets nodejs/jest envs),
  2. run `yarn oxlint --suppress-all` to add the `import/unambiguous` suppression entries to root `oxlint-suppressions.json` — the glob does NOT disable that rule (all 132 existing jest configs carry suppression entries),
  3. re-run `yarn lint:misc --write oxlint-suppressions.json` from the root because `--suppress-all` strips the file's trailing newline (oxlint variant of [ts-005]), which would fail `lint:misc:check` in CI.
- **[ts-031] Broken local watchman silently yields empty jest test lists**: If `yarn jest --listTests` prints 0 files with exit 0 on this machine, suspect the Homebrew watchman install (dyld: `libfmt.11.dylib` missing). Pass `--no-watchman` for local runs to bypass it, or `brew reinstall fmt watchman`. Never treat the empty list as "no tests exist" — verify with the flag before debugging configs.
- **[ts-032] MetaMask/core: new required controller-state fields break state literals repo-wide — diagnose via `yarn lint:tsc:check`**: adding REQUIRED fields to a controller State type breaks every literal constructing it (fixtures, data-source tests, middlewares, migrations, selectors — files the PR never touched), and only the new `lint:tsc:check` (`tsc --build tsconfig.lint.json`, typechecks TESTS unlike `yarn build`) sees them. Fix each literal by adding the fields (`{}` for map fields), and bump `tsc-suppressions.json` counts ONLY for idioms main already suppresses in that file.
  - Beware `tsc --build` incremental reprinting + truncated tool output: enumerate errors from the FULL check log (`grep '^  packages/' | sort | uniq`), not a head window; a later run after edits may surface errors the first run's truncation hid.
- **[ts-033] MetaMask/core CI Build / lint:tsc:check can pass via stale tsbuildinfo caches while fresh local builds fail**: a ~33s "Build (24.x)" full-monorepo pass = projects skipped via restored build caches; a fresh local `yarn build` / `yarn lint:tsc:check` can fail on identical content (seen: main's perps-controller TS2353 ×2 + stale suppressions, byte-identical to our tree, CI green). When local-red/CI-green on the same tree: verify identity (`git diff HEAD origin/main -- <pkg> <config>`), confirm no hotfix (`git log <last>..origin/main`), then treat it as a CI cache artifact — CI's verdict gates the PR. Never fix another package's breakage in your PR; leave it for main's hotfix.
- **[ts-034] Remote branch may move between turns; fetch before push, re-measure after rebase**: In multi-turn PR work, the user may merge `main` into the feature branch (or push) via the GitHub UI between turns. Before amending/pushing: `git fetch origin <branch>` and compare `git log --oneline -1 origin/<branch>` vs local. If `git push --force-with-lease` is rejected with "stale info", do NOT force: rebase onto `origin/<branch>` (`git checkout --theirs` for AA conflicts where your replayed commit is a strict refinement), then push a plain fast-forward. After the rebase, the merged main may change tests/source in the touched packages — re-run and re-measure any coverage thresholds that were calibrated to exact measured values on the old base, then re-amend.
- **[ts-035] Vacuous verification: grep/find over missing input looks like success**: When verifying "X is absent", first prove the INPUT exists. `ls dir | grep -c x` → 0 and `grep x file || echo 0` both print "0/none" when `dir`/`file` don't exist (pipe exit status is grep's, not the producer's). Guard with `test -f <file> && ...`, `set -o pipefail`, or make the producer fail loudly (`ls` with no dir errors — check stderr, not just stdout count). Treat any "absence ✓" claim made without a proven-present input as unverified.
- **[ts-036] PR body/title and /tmp staging files are shared mutable state across concurrent agent sessions — verify before trust**: PR metadata is not git state; a maintainer or concurrent session can overwrite your PR's body (seen: PR #10230's body replaced with another PR's description) and clobber generic /tmp staging paths (seen: `/tmp/pr-body.md` flipped to another PR's body mid-turn between commands).
  1. after any external interference signal (push rejected = someone merged into your branch), re-fetch title AND body and grep-verify identity BEFORE any body edit;
  2. `gh pr edit --body-file` only after a grep-assert that the staging file contains your feature's keywords, `&&`-chained so a failed assert blocks the edit;
  3. never reuse generic /tmp filenames across commands — use unique paths (e.g. `pr-body-restore-10230.md`) and re-verify content immediately before use;
  4. PR bodies have no git history and comments rarely mirror them — realistic recovery is reconstruction from knowledge + CHANGELOG + title (GraphQL note: PRs resolve via `pullRequest(number:)`, not `issue(number:)`; REST events API is rate-limited first).
- **[ts-037] MetaMask/core: never hand-bump `tsc-suppressions.json` counts for feature-added sites — use inline `@ts-expect-error` instead**: the lint-tsc system fails on both uncovered (found > suppressed) AND stale (suppressed > found) counts, so JSON bumps must exactly track live error counts through every future main merge and keep the PR touching the root suppression file. Repo style for feature-added test idioms: `// @ts-expect-error -- <reason>` directly above the line where the error starts (for TS2554 extra-argument errors that is the first EXTRA argument's line, not the call line); TS2578 "Unused '@ts-expect-error' directive" in `yarn lint:tsc:check` self-checks placement. Keep main's own suppressed sites on the JSON counts (never prune them in a feature PR).
